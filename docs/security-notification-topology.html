セキュリティ通知の配送トポロジー

Security Hub / GuardDuty / Inspector / AWS Health の通知を Slack などの 1 か所に集める配置を、アカウント × リージョン × サービスの表で 3 ケース示す。使う仕組みは「委任」「集約」「統合」「直通」の 4 つで、どのケースもこの組み合わせで説明できる。対象は Security Hub CSPM。リージョンは東京（ホーム）と us-east-1（グローバルサービス）を例にする。Inspector は Hub 経由でホームに届くが、CVE の件数が多いため examples では既定で Slack 通知から除外している。

4 つの仕組み

委任Organizations の委任管理者。管理アカウントが別アカウントにサービスの管理権限を付与する関係。Security Hub / GuardDuty / Inspector では管理者アカウントの同じリージョンにメンバーの finding が複製される。Health では組織ビューで全アカウント分が 1 フィードになる 集約Security Hub のリージョン集約。リンクリージョンの finding をホームリージョンに複製する。Security Hub にしか無い機能で、GuardDuty / Inspector / Health にリージョン集約は無い 統合Security Hub の統合。GuardDuty / Inspector などの finding を同アカウント・同リージョンの Security Hub が取り込む。Health も取り込むがセキュリティ関連の一部だけ 直通EventBridge ルールが同リージョンの SNS トピックへ発行する。通知経路はこの直通ルールを置くリージョンにだけ存在する

4 つは 1 本の配送経路ではない。委任はアカウントを、集約はリージョンを、統合はサービスを越える別々の仕組みで、finding は「統合 → 委任 → 集約 → 直通」の順に通る場合もあれば、Health のように直通だけの場合もある。

ケース 1: 委任管理者 = セキュリティ集約アカウント（推奨形）

複数アカウントを持つ組織では、AWS の Security Reference Architecture に沿って「セキュリティ集約アカウント」を委任管理者にし、通知経路をそこに 1 組だけ置くのが標準形。管理アカウントは委任するだけで、ワークロードも通知経路も持たない。

アカウントリージョンSecurity HubGuardDuty / InspectorAWS Health通知経路（EventBridge → SNS）
管理アカウントOrganizations の root 東京 / us-east-1 委任元委任管理者に集約アカウントを指定 委任。自身では有効化しない 委任元同じく集約アカウントを委任管理者に 委任 委任元組織ビューを有効化し、委任管理者を指定 委任（サポートプラン不問） 置かない
セキュリティ集約アカウント委任管理者。通知経路はここだけ 東京ホーム 管理者（ホーム）全メンバーの東京分を受信 委任。us-east-1 分は 集約 で到着。ここで全 finding が揃う 管理者全メンバーの東京分を受信 委任。Hub へ 統合（通知は Hub 経由に一本化） 組織ビュー全メンバーの東京発イベントを 1 フィードで受信 委任 直通 Hub ルール（重要度・Workflow で絞る）+ Health ルール → SNS 東京 → Chatbot / Lambda
us-east-1リンク 管理者（リンク）全メンバーの us-east-1 分を受信 委任 → 東京へ 集約。ルールは置かない 管理者受信 委任 → Hub へ 統合 → 東京へ 集約 組織ビューグローバルサービス + us-east-1 発（+ us-west-2 のバックアップ）を受信 委任 直通 Health ルールのみ → SNS us-east-1 → Chatbot / Lambda（Lambda はクロスリージョン購読）
メンバーアカウントdev / prod / … 各ワークロード 東京 メンバー設定ポリシーで有効化・標準を一括適用（中央設定）。finding は集約アカウント東京へ 委任 メンバー有効化は自動。finding を同リージョンの Hub へ 統合、管理者へ 委任 発生元自アカウントのイベントが組織ビュー経由で集約アカウントへ 委任 置かない
us-east-1 メンバー同上。finding は集約アカウント us-east-1 へ 委任（その後 集約 で東京へ） メンバー同上 統合 → 委任 発生元同上 委任 置かない

読み方: メンバーの finding は「委任」でアカウントを越え、「集約」でリージョンを越え、「統合」でサービスを越えて、集約アカウントの東京に 1 か所に集まる。そこにだけ「直通」の EventBridge ルールと SNS を置く。Health だけはリージョン集約が無いので、us-east-1 にもう 1 本ルールが必要。

集約アカウントに寄せる理由

  • 通知ルール・SNS・Chatbot・調査 Lambda が 1 組で済み、アカウントが増えても経路を増やさない
  • メンバー側で通知設定を消されても、管理者側の複製は止まらない
  • 中央設定でメンバーの Hub 有効化・標準・コントロールを一括管理し、設定ドリフトを防ぐ

集約・統合・直通の使い分け

  • アカウント横断は各サービスの委任管理者（finding が管理者アカウントに複製される）
  • リージョン横断は Security Hub のリージョン集約のみ。GuardDuty / Inspector は Hub への統合で乗せる
  • Health は組織ビューでアカウント横断、リージョンは各リージョンの直通ルール（グローバルは us-east-1）

前提と注意

  • 委任管理者の指定は管理アカウント側の作業。examples の case1-delegated-security-account/management がその部分
  • Health 組織ビューの有効化は管理アカウントのコンソール操作（全プラン）。CLI / API は Business 以上。Terraform リソースは無い
  • 東京 + us-east-1 以外のリージョンは「リンクリージョンに含めるか、無効化するか」を設定ポリシーで決める

管理アカウント = 集約アカウントにできるか

  • GuardDuty は管理アカウントを委任管理者に指定できるが公式に「非推奨」。Security Hub はローカル構成なら指定できる（非推奨・管理アカウント側で手動有効化が必要）が、本資料が前提にする中央設定では管理アカウントを委任管理者にできないと明記されている
  • Health の組織ビューは管理アカウントでしか有効化できないが、閲覧・受信はメンバーアカウントへ委任するのが AWS の推奨（管理アカウントを絞ったまま運用チームに見せるため）
  • Inspector は公式ドキュメントに管理アカウント指定の可否・推奨の明記が無い。委任管理者は全リージョンで同一アカウントが必須で、管理アカウント自身の Inspector 有効化は委任管理者側から行う手順になっている
  • 避ける理由: 管理アカウントには SCP が効かない、ワークロード（SNS / Lambda / 調査パイプライン）を置かないのが原則、請求管理者とセキュリティ管理者のアクセス分離
  • 結論: 中央設定を使う限り管理アカウント = 集約アカウントは成立しない。ローカル構成で妥協する形はケース 2 として下に示す

ケース 2: 管理アカウント = セキュリティ集約アカウント（やむを得ない場合）

アカウントを増やせない、運用者が同一、といった事情で管理アカウントに集約する形。examples/security-notification-topology/case2-management-account がこの表の実装。AWS は非推奨だが動く。最大の違いは Security Hub の中央設定が使えないこと（中央設定では管理アカウントを委任管理者にできない）。そのためローカル構成になり、メンバーの有効化・標準・コントロールをアカウントごと・リージョンごとに揃える作業が残る。

アカウントリージョンSecurity HubGuardDuty / InspectorAWS Health通知経路（EventBridge → SNS）
管理アカウント = 集約アカウント委任元と委任先が同一。SCP が効かない 東京ホーム 委任元 + 管理者（ローカル構成）自分自身を委任管理者に指定 委任（非推奨・手動で Hub 有効化）。メンバーの東京分を受信、us-east-1 分は 集約。設定ポリシーは使えない 委任元 + 管理者自分自身を委任管理者に 委任（GuardDuty は公式に非推奨、Inspector は可否の明記なし）。自動有効化 ALL はリージョンごとに設定。Hub へ 統合 組織ビュー（本来の有効化主体）委任せずそのまま受信。全メンバーの東京発イベントが 1 フィードで届く 直通 Hub ルール + Health ルール → SNS 東京 → Chatbot / Lambda。通知経路・調査 Lambda が管理アカウントに載る
us-east-1リンク 管理者（リンク）各リージョンで個別に委任管理者を指定する必要がある 委任。受信分は東京へ 集約 管理者同上（リージョンごとに指定） 委任 → 統合 → 集約 組織ビューグローバル + us-east-1 発（+ us-west-2 バックアップ）を受信 直通 Health ルールのみ → SNS us-east-1 → Chatbot / Lambda
メンバーアカウントdev / prod / … 東京 メンバー既存アカウントはリージョンごとに手動で有効化・標準を選択（自動有効化は新規アカウントのみ）。finding は管理アカウントへ 委任 メンバー自動有効化 ALL なら既存も対象。統合 → 委任 発生元組織ビュー経由で管理アカウントへ 委任 置かない
us-east-1 メンバー同上（東京とは別に有効化・標準選択が必要）委任 → 集約 メンバー同上 統合 → 委任 発生元同上 委任 置かない

推奨形との差

  • 中央設定が使えない → 設定ポリシー無し。メンバーの有効化・標準・コントロールはアカウント × リージョンごとに手作業で揃え、ドリフトを自分で検知する
  • 委任管理者の指定もリージョンごと（中央設定なら home + linked に自動展開される）
  • Health だけは差が無い。組織ビューは管理アカウントの機能なので、むしろ委任の手間が省ける

やるなら守ること

  • 管理アカウントに置くのは Hub / GuardDuty 管理者と通知経路（SNS / Chatbot / Lambda）まで。他のワークロードは一切載せない
  • SCP が効かないため、IAM ポリシーと MFA で通知経路と Agent Space ロールへのアクセスを絞る。調査 Lambda のロールはメンバーへの読み取りに限定する
  • 将来アカウントを増やせるようになったら、集約アカウントを分離して委任先を切り替える（GuardDuty / Inspector はメンバーの有効化状態を維持したまま委任先を変更できる）

ケース 3: 1 メンバーアカウント（委任なし）

委任管理者にはなれず、アカウントも増やせない前提。使える道具は「Security Hub のリージョン集約」「Hub への統合」「各リージョンの直通ルール」の 3 つだけなので、それをどう配置するかが論点になる。examples/security-notification-topology/case3-single-member がこの表の実装。

アカウントリージョンSecurity HubGuardDuty / InspectorAWS Health通知経路（EventBridge → SNS）
メンバーアカウント委任なし・単独運用 東京ホーム ホームFSBP を有効化。他リージョンからの 集約 を受ける。グローバルリソースのコントロール（IAM.* など）はここだけで評価し、他リージョンでは無効化 全機能有効Runtime / S3 Malware などワークロード依存の保護はワークロードがあるリージョンだけ。Hub へ 統合、ネイティブルールは置かない 直通Event + Abuse の 2 種を 直通 で SNS 東京へ 直通 Hub ルール（GuardDuty 全件 / コントロール HIGH+）+ Health ルール → SNS 東京 → Chatbot（+ 任意の Lambda）。EventBridge ターゲットに DLQ。ルールを「SNS に publish してから Workflow を NOTIFIED にする」Lambda 経由にすると再通知が止まる
us-east-1リンク リンクCloudFront / IAM などグローバル系の finding 用。東京へ 集約。ルールは置かない 基礎データソースのみワークロードが無いので Runtime / Malware 系は不要。Hub へ 統合 直通グローバルサービス + us-east-1 発 + us-west-2 バックアップを 直通 で SNS us-east-1 へ 直通 Health ルールのみ → SNS us-east-1 → Chatbot（+ 任意の Lambda、クロスリージョン購読）。CloudFront のアラームもこのリージョンに置く
他リージョンワークロード無し リンクに追加集約リンクを全リージョンに広げる（ALL_REGIONS、将来のリージョンも自動）。グローバルリソース系コントロールは無効化して重複 finding を消す。使わないリージョンは無効化して費用を絞る選択も可 基礎データソースのみGuardDuty は不正利用検知のため全リージョンで有効にし、Runtime / Malware / RDS / Lambda 保護は OFF にして費用を絞る。Hub へ 統合 → 東京へ 集約。Inspector はスキャン対象が無いので無効化 バックアップ配信で代替リソースが無いのでリージョン固有イベントは稀。us-west-2 に 1 本だけ直通ルールを置けば、全リージョンのアカウント固有イベントを 1 か所で受けられる（public イベントは含まれない） 置かない（us-west-2 の Health ルールだけ例外。communicationId で東京 / us-east-1 との重複排除）

集約の軸

  • アカウント横断は無いので、リージョン横断は Security Hub の集約 1 本に寄せる。GuardDuty / Inspector は統合で Hub に乗せ、ネイティブルールは持たない
  • Health だけは集約機能が無い。東京・us-east-1 の直通に加え、他リージョンを拾うなら us-west-2 のバックアップ配信を使う
  • SNS トピックはルールを置くリージョンごとに 1 本（東京・us-east-1、他リージョン分を拾う場合は us-west-2）。購読者は Chatbot と Lambda の 2 つで固定

通知量の制御

  • コントロール finding は「失敗の発生ごとに 1 回」にする。ルールを SNS publish → NOTIFIED 更新の Lambda 経由にすれば、再評価のたびの再通知が止まる（PASSED → FAILED で NEW に戻るので再発は拾える）
  • グローバルリソースのコントロールをホーム以外で無効化し、17 リージョン分の複製 finding を消す
  • 受容済みのリスクは Security Hub で SUPPRESSED にする。除外条件は EventBridge パターンではなく Security Hub 側に持たせる

配信の信頼性

  • EventBridge → SNS のターゲットに DLQ（SQS）を付け、失敗イベントの本体を 14 日残す。必要なら EventBridge アーカイブでリプレイ
  • SNS の配信ステータスログを有効化し、Chatbot への失敗を CloudWatch Logs に残す
  • Lambda の DLQ 滞留にアラームを付ける（Lambda 経路が止まっても Chatbot 経路は生きるが、止まったことに気づく手段が要る）

管理の一貫性

  • 全リージョンの有効化状態を Terraform で管理する。provider は module の for_each に渡せないので、リージョンごとに module ブロックを明示する
  • 標準は FSBP に統一する。旧版 CIS を併用すると二重評価と旧版コントロールの通知が増える
  • 将来アカウントが増えて委任管理者になれるなら、上の「推奨形」に移行する。その際もホーム = 東京、リンク = us-east-1 の設計は引き継げる
